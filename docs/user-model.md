# Authentication database contract

Prepared on branch `abdullah/auth-user-model` for Muhammad's authentication routes.
No routes, server configuration, dependencies, or connection credentials are changed.

## Schema: `backend/models/User.js`, collection `users`

| Field | Stored type | Rules |
| --- | --- | --- |
| `_id` | ObjectId | Generated by MongoDB/Mongoose |
| `name` | String | Required, trimmed, maximum 100 characters |
| `email` | String | Required, trimmed, lowercase, maximum 254 characters, basic email syntax |
| `password` | String | Required; plaintext accepted only in memory, saved as a salted scrypt hash |
| `createdAt`, `updatedAt` | Date | Automatic timestamps |

New passwords must be 12–128 characters, not whitespace-only. Passwords are never trimmed.
This is a proposed policy: coordinate frontend and route validation with Muhammad.
Unknown schema fields and non-string name/email/password values are rejected.

## Password handling

Uses asynchronous Node.js `crypto.scrypt`, N=131072, r=8, p=1, a random 16-byte
salt, and a 64-byte derived key. No additional npm package is needed. The format is
`scrypt$131072$8$1$<salt-hex>$<key-hex>`. This follows an OWASP scrypt parameter set.
Hashing is automatic on `save()`/`User.create()` and happens only for modified passwords.
Do not hash in the route as well, and do not use bcrypt.compare() with this format.
`comparePassword()` derives the candidate key and uses `timingSafeEqual()`.

Passwords are excluded from normal queries (`select: false`) and removed by the JSON
and object transforms even after explicit selection. Never return raw validation errors,
raw documents from `User.collection`, or `.lean()` results that explicitly select passwords.
Mongoose validation error objects can contain submitted values; send a sanitized message.

Query update/replacement methods, `insertMany()`, and `bulkWrite()` are intentionally
blocked because they bypass save hooks. Use document assignment followed by `save()`
for profile/password changes. Raw driver calls, `User.collection`, and deliberately
disabled middleware are outside this model's protection and must not handle auth writes.

## Email uniqueness

The schema declares one unique index on normalized email. `unique` is an index,
not a Mongoose validator. Run `await User.init()` after connecting, before accepting
registrations, so the index is ready. MongoDB enforces uniqueness even during concurrent
requests. Handle duplicate-key error `code === 11000` as HTTP 409. Do not rely on a
find-before-create check alone. If existing users contain conflicting emails, index
creation will fail; review duplicates rather than deleting data automatically.
Lowercase/trim is our application identity policy; no provider-specific dot/plus rewriting.

## Integration example for Muhammad

```js
const User = require("../models/User"); // From a file in backend/routes

// After MongoDB connection succeeds, during startup:
await User.init();

// Registration: pick only supported fields from the request body.
const { name, email, password } = req.body;
const user = await User.create({ name, email, password });
// user.toJSON() removes the password, including the hash.
res.status(201).json({ success: true, data: user.toJSON() });

// Login (in a separate handler): reject non-string email/password first.
const loginEmail = req.body.email.trim().toLowerCase();
const loginUser = await User.findOne({ email: loginEmail }).select("+password");
const matches = loginUser && await loginUser.comparePassword(req.body.password);
// If !matches, return the same generic 401 response for unknown email/wrong password.
// Session/JWT issuance, rate limits, and auth routes remain Muhammad's responsibility.
```

Suggested responses: invalid fields 400, duplicate email 409, invalid login 401,
unexpected failures 500 with a generic message. Never log credentials or request passwords.

## Tests and run instructions

Use Node.js 20.19+ (verified on Node 24) and the existing locked dependencies:

```sh
cd backend
npm ci
node --test tests/user.test.js
```

Without `TEST_MONGODB_URI`, six model tests run and the database suite is explicitly
skipped. For full integration tests, put `TEST_MONGODB_URI` in your local ignored
`backend/.env`, using the team's private Atlas credentials and database name
`inventory_management_test`. Do not paste its value into GitHub or team messages.

```sh
node -r dotenv/config --test tests/user.test.js
npm test
```

The suite refuses any URI whose database name is not exactly `inventory_management_test`;
it never falls back to `MONGODB_URI`. It creates a `users` collection and email index if
needed, waits for the index, and deletes only generated test IDs in a finally block.
It never drops databases/collections or deletes existing users.

Coverage: normalization and required/type/length validation; no password in JSON;
blocked hashing bypasses; actual stored salted hashes and timestamps; sequential and
concurrent duplicate emails; retrieval; correct/wrong password comparison; invalid
writes; save without rehash; password change; cleanup. The test password literals are
disposable fixtures, not Atlas or real user credentials.
